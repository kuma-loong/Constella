# Profile 个人看板设计

状态：交互设计提案，2026-09-06。配套原型为 `docs/design/profile/index.html`，使用明确标记的示例数据；未接入 API、未替换当前 Profile。

## 界面文案与图形规范

界面统一使用英文，面向实验室成员和技术人员。采用 GPU hours、Busiest hours、Time with active jobs、Active days、Most-used GPU、Recent jobs、Account settings 等直接名称。页面保留用户做判断所需的单位、时区和共享 GPU 提示；UID、归属算法、查询接口、路由参数等细节仅保留在本文档。预览限制用简短英文说明，不把实现方案展示为产品文案。

主统计采用细钴蓝趋势线、极淡面积、每日数据点和日期指示线，代替宽柱。三个纵轴刻度帮助读取真实数量；曲线经过每日值并限制在相邻值之间，数据点才表示当日总量，不推断日内使用。悬停查看日期与卡时，点击或触摸筛选任务；键盘方向键选择日期，Enter 应用。右侧时段图使用连续活动轮廓；桌面布局约占主统计区 43% 宽度。横轴每小时设短刻度，图宽至少 320 px 时每 2 小时显示标签，更窄时每 3 小时显示标签。高峰时段使用加强的钴蓝背景、边界与加粗曲线，并标注 Peak。GPU 型号占比使用单条比例带。

## 1. 定位与设计决策

个人页是「我的 GPU 工作记录」：了解最近的计算活动，回到自己的任务，继续分析。保留 Profile 导航名，页面标题用「Your work, at a glance.」；账号绑定、显示名编辑迁到 Account settings。

设计读法：面向 GPU 开发者的个人工作看板，沿用 Constella 的密集控制台结构，借鉴 Strava 的个人记录与活动历史。`DESIGN_VARIANCE 4 / VISUAL_DENSITY 8`；日常操作 `MOTION 2`，用户要求的重点统计过渡提升到 4。

Strava 参考：[Activity History](https://support.strava.com/en-us/articles/15402014-viewing-your-activity-history-on-strava)、[Personal Heatmaps](https://support.strava.com/en-us/articles/15402028-personal-heatmaps)。借鉴「个人数据 → 有意义的发现 → 可回看的活动」的信息组织；下述动画是为 Constella 设计的方案，不声称复刻 Strava 的具体实现。

## 2. 页面结构

```text
Constella / 现有全局导航                             用户菜单
PROFILE / Your workspace                          Account settings
姓名 · 绑定节点数量          正在运行 2 → 最近任务
统计周期 [最近 7 天 / 最近 30 天]  日期 · 时区
───────────────────────────────────────────────────────────
GPU 使用时长                                 你的使用节奏
126.4 GPU·h                                 20:00–23:00
较前一等长周期 +18.6 GPU·h                    GPU 活跃高峰
每日卡时趋势图 / 当前选中日期                   24 小时分布
───────────────────────────────────────────────────────────
任务运行时长 46.2 h | 活跃 6 天 | 常用 GPU H100 · 72%
───────────────────────────────────────────────────────────
最近任务  [全部 / 运行中 / 已结束]  搜索任务、节点、PID
运行中任务置顶 → 按最后观测时间降序             打开完整 Jobs
任务名 / 状态 / 节点与 GPU / 起止时间 / 时长 / 查看
───────────────────────────────────────────────────────────
按 GPU 型号的使用分布               统计覆盖与数据更新时间
```

首屏的大数字、每日活动形状、活跃时段形成个人辨识度。主数字占较大的视觉面积；辅助数字共享一条分隔数据带。避免把每个数包进独立卡片。桌面近期任务标题尽可能落在首屏附近；运行中数量始终可以直接定位任务区。

日期默认最近 7 个日历日（含今天截至当前时刻），可选最近 30 天。显示准确起止日期及 IANA 时区；上一周期按相同本地日期边界及截至时间比较。日界线计算需处理夏令时；时长一律由真实秒数计算，不假定每天均为 24 小时。运行中区不受历史周期影响；历史任务按周期内有交集筛选。

## 3. 看板指标与口径

| 展示 | 计算定义 | 交互与缺失处理 |
| --- | --- | --- |
| GPU 使用时长 / GPU·h | 本人有可归属进程的物理 GPU 观测时间。同一用户、节点、物理 GPU 的重叠区间取并集，再跨卡求和；同卡多个进程不重复计时。4 卡运行 2 h = 8 GPU·h。 | 选择每日数据点筛选历史任务；再点清除。口径通过可聚焦的说明按钮查看。不是利用率加权时长，也不代表独占占用或算力产出。 |
| 任务运行时长 / h | 本人至少有一个 GPU 任务被观测到的时间并集，跨任务和节点去重。 | 作为卡时辅助解释，4 卡同时运行 2 h 仍为 2 h。使用「观测」说明，避免承诺完整生命周期。 |
| GPU 活跃高峰 | 按本地小时汇总观测卡时，选累计卡时最高的连续 3 小时窗口，允许跨午夜。 | 展示 24 小时活动轮廓图；不是人的工作时间。默认至少 3 个有效活动日才生成高峰文案；平峰/并列显示「分布较均匀」或并列时间，不强行推断习惯。 |
| 最常用 GPU | 按型号合并物理卡时，展示第一名、卡时和占比。 | 例：H100 · 72%；展开分布可查看节点与物理卡。未知型号单列，分母包含所有已归属卡时。 |
| 活跃天数 | 本地日期内存在有效 GPU 观测区间的日期数。 | 仅用于记录，不设置消耗算力的排行榜或连续签到压力。 |
| 运行中任务 | 当前有新鲜节点快照证实仍在运行的任务组数。 | 点击切到运行中筛选。节点失联显示「状态未知」，不能把消失当作执行成功。 |

增长显示中性文案「较上一周期多 18.6 GPU·h」，不用绿色上涨箭头评价效率。上一周期无数据则不展示百分比；上一周期为 0 可以显示绝对增量。统计覆盖不足时保留已观测值并标「部分记录」，不推算完整月数据。

进程现有 first_seen/last_seen 只给观测跨度，可能包含采样缺口。第一阶段若无法重建连续观测区间，应明确显示「按观测跨度估算」，禁止给出无法验证的 100% 覆盖率。后续使用连续片段聚合，超过采集容差的缺口不计时。当前卡时口径与 Overview 的 session 累加存在差别，新增共享聚合前不能直接把现有排行榜数字当作个人卡时。

## 4. 最近任务与工具链

选择「列表 → 任务抽屉 → 完整 Jobs」，个人页承担快速确认，Jobs 承担完整分析。

1. 默认显示最多 8 行；运行中置顶，其余按 last_seen 降序。显示任务名、运行/结束/未知、节点、GPU 型号与数量、开始/最后观测时间、观测时长。搜索支持任务名、节点、PID；输入宽度不随结果变化。历史日期筛选显示可清除标签，运行中任务不因选中过去日期消失。
2. 点击查看打开右侧抽屉，URL 建议 `/profile?job_key=…`；列表筛选、滚动位置和周期不丢失。手机全宽抽屉。Escape/关闭恢复焦点到来源行，浏览器后退关闭抽屉。
3. 抽屉分为 Overview、GPU、Performance。Overview 复用进程元信息、命令复制和设备清单；任务组可含多个进程，先显示组摘要，再选进程，不能把组信息硬塞成单一 ProcessDetail。
4. GPU 页签默认一条利用率曲线，可切显存/功率；Performance 使用现有 Jobs 的 job performance 查询能力。按任务时间范围裁剪，用懒加载避免列表为每个任务请求曲线。
5. 每张曲线明确标「任务所在 GPU 的指标」，有同卡并发时显示实际提示。历史曲线过期时保留任务元信息，给出可用范围和采样精度。不要画零值线冒充无记录。
6. 「在 Jobs 中分析」进入完整页面并选中相同 job_key、时间、设备、指标；返回恢复个人页上下文。现有 PID + node_id + since 链接保留兼容，但精确 job_key 深链需要新增，避免 PID 重用和默认首条误选。
7. 全局 Performance 页面保留实时跨设备诊断；任务历史 Performance 优先在 Jobs 中深入。只有「查看当前设备」才跳全局 Performance，并明确「当前实时」与「该任务历史」的区别。

现有监控判断的是观测状态，默认只用「运行中 / 已结束 / 状态未知」。没有退出码或调度器结果时，不展示「成功 / 失败」。GPU count、任务分组复用现有语义；跨节点分布式训练在没有稳定调度器 ID 时保持多个任务，不按相似命令猜测合并。

## 5. 轻量交互动效

日常看板：动作短、因果明确。每次后台刷新不重播整屏。

| 时机 | 动效 | 时长与退化 |
| --- | --- | --- |
| 首次有效数据到达 | 大数字从轻微下移 8 px 归位；每日曲线从左向右描绘，末段高峰高亮。 | 450–700 ms，错峰总长不超过 900 ms；先呈现可读取的最终文本，不逐帧播报。 |
| 7/30 天切换 | 数值平滑变化；曲线更新并重新描绘，日期范围同步更新；高峰标记同步移动。 | 350–500 ms。快速连点取消前一帧动画，从当前视觉值到新值。 |
| 日期选择 | 日期指示线和对应数据点强调，日期与卡时说明更新；历史任务区应用日期过滤。 | 120–180 ms；不滚动劫持，不强行跳到页面下部。 |
| 打开任务 | 抽屉从右滑入，内容随后出现；图表准备好再绘制。 | 200–240 ms；手机仅短距离位移。 |
| 后台刷新 | 仅变化数值更新；过渡不改变行高，不自动重排用户正在操作的行。 | 120 ms；显示更新时间，离开页面停止轮询。 |

不引入 WebGL、粒子或新动效依赖。原生 CSS transform/opacity + 有限 requestAnimationFrame 足够；uPlot 专注任务曲线，不能每帧重建图表实例。

## 6. 视觉、响应式与可访问性

- 沿用 Geist / Geist Mono、方形数据面、6 px 控件、4 px 标签。GPU 图用 cobalt `--telemetry`，绿色只表示运行、选中等状态。大型卡时数字用文本色，避免满屏强调色。
- 桌面采用约 1.3:1 的主统计/节奏区，两者共享分隔线。辅助指标用一条数据带；任务用紧凑的连续行。
- 760 px 以下顺序为身份与设置 → 周期 → 主统计 → 使用节奏 → 指标带 → 最近任务 → GPU 分布。周期与搜索控件可换行，图横轴降刻度，行改两行元信息；无需横向页面滚动。
- 320 px 仍可用；任务详情有独立可滚动内容及始终可达的关闭按钮。所有操作支持键盘；趋势图配日期/单位读数与键盘焦点，触屏点击可固定详情。
- 明暗模式均采用既有 token；单独检查弱化文本、tooltip、图线和焦点环。动画尊重 prefers-reduced-motion，无闪烁、无限循环或滚动接管。

## 7. 账号设置与异常状态

正式建议新增 `/profile/settings`，保留 AccountPage、AccountBindingForm 的既有功能，顶部「返回个人看板」。`/account` 可迁到设置页并兼容旧入口；当前代码会把它重定向到 `/profile`，需同步调整 canonicalLabPath/isPath/parseRoute。用户菜单增加 Account settings，注册绑定流程保留。

| 状态 | 页面行为 |
| --- | --- |
| 首次加载 | 固定大小的文字/图表骨架；禁止用 0 代替尚未拿到的数字。 |
| 无活动 | 「这段时间还没有 GPU 记录」；保留日期选择与查看节点入口。 |
| 无绑定 | 一条简短提示和「连接节点账号」入口；设置页承接完整表单。 |
| 旧 agent 无 UID | 「部分记录无法确认归属」；未知记录不按用户名偷偷归入，提供设置/管理员说明。 |
| 当前角色 viewer | 显示可见的个人记录；无归属记录时解释只读身份，入口遵从现有权限。 |
| 单区块请求失败 | 本区块错误与重试；其他区块继续工作。已有数据可保留并标更新时间。 |
| 节点离线 | 任务状态未知和最后观测时间；历史统计仍可浏览。 |
| Performance 不支持 | 明确能力提示；仅查询 supported_metrics，NVLink 不支持就不展示对应曲线。 |
| 历史已过期 | 任务列表仍可显示已保存元信息；图表显示可用区间/已过期，不能回退到错误时段。 |

原型的状态选择器用于评审空、未绑定、部分记录和错误状态，不属于正式页面。

## 8. 数据与实现落点

已核实的代码：`frontend/src/lab/AccountPage.tsx` 当前以显示名与账号绑定为主；`LabRoot.tsx` 控制 Lab 专属路由；`ProcessDrawer.tsx` 有详情/复制命令/Jobs 跳转；`analytics.ts` 中 Jobs 已查询 GPU 和 Performance 历史；`process-details.ts` 的 jobsHref 目前支持 PID、node_id、since。

数据底座已有 process_sessions.user_uid、绑定的 node_id/unix_uid/valid_from/valid_to，以及进程 GPU 使用区间。但现有 Overview 是按 user 字符串聚合并截断前 20 名；不能在浏览器对这个结果过滤作为个人统计。最近任务也不能先取全局 80 条再过滤，否则活跃集群会漏掉本人任务。

建议新增 Lab 范围的服务端聚合（以下为设计合同，非现有接口）：

```text
GET /api/lab/me/dashboard?range=7d&timezone=Asia%2FShanghai
  period, generated_at, coverage, warnings
  gpu_hours, active_seconds, active_days, comparison
  daily_usage[], hourly_usage[], gpu_models[], running_count

GET /api/lab/me/jobs?range=7d&status=all&q=…&cursor=…
  items[], next_cursor, generated_at
  每项包含稳定 job_key、可用曲线范围、状态新鲜度
```

两个接口均从已认证会话解析本人，服务端先应用身份归属再聚合/分页，不接受前端任意 user_id 来替代授权。曲线详情同样检查该任务归属，再复用后端查询；前端隐藏行不能承担权限控制。限定在 Lab 版，基础版无需引入身份依赖。

归属为 `(node_id, user_uid)` 与绑定有效期及观测区间求交：保留已解除绑定的历史有效区间；重分配后按时间切开；绑定前记录默认不追溯归属。合并多个账号时统一到 Lab user_id，再对本人同卡重叠时间去重。null UID 留在未归属桶，不能跨节点按用户名匹配。

第一阶段仅使用已存在进程采集策略记录的 GPU 工作负载。对 agent 版本、缺口与保留窗口返回 coverage/warnings；不得承诺记录被过滤的桌面进程或重建从未采集的历史。缓存按 user_id、绑定版本、周期、时区隔离；绑定变更失效。建议主看板 60 秒刷新，运行任务沿用现有实时快照或 10 秒轻查询，隐藏页面停止；这是建议值，实施时按真实负载验证。

前端新增 ProfilePage、ProfileSummary、RecentJobs；共享任务查询与曲线视图从 analytics.ts 按责任抽取，供 Jobs 与抽屉共用。避免在 Profile 复制大型 innerHTML 渲染器。样式放入现有 analytics/lab/responsive 对应文件，新增前检查文件长度，超过 2,000 行前按责任拆分。Performance 组序、单位、可选指标规则继续沿用。

## 9. 分期与验收

第一期：归属聚合 + 7/30 天看板 + 最近任务 + 复用进程详情 + 精确 Jobs 深链 + 账号设置迁移。包含基础过渡，完成核心体验闭环。

第二期：抽屉内 GPU/Performance 预览、连续观测片段与采样覆盖细化、按型号下钻。提取共享逻辑之后再嵌入图表。

后续可选：任务备注/自定义名称、收藏任务、手动比较两次运行。这些分别需要持久化或比较能力，不在第一期承诺。暂不加入效率评分、计算量排行榜、能耗估算和任务成功率。

正式实现验收：多卡与同卡多进程去重正确；跨节点同名不同 UID 不串号；绑定解除/重分配按历史有效期；旧 agent/null UID 可降级；结束与未知不误报成功；7/30 天同源聚合；深链选中唯一任务；任务历史只读 GPU 设备曲线；不支持 NVLink 不发请求；过期数据与 0 区分；快速切换避免过期响应覆盖；reduced-motion/键盘/明暗/320–760 px 可用。

本次仅提供设计文档与独立原型，验证原型 JS、主要交互、桌面明暗和手机布局以及 git diff --check。正式接入后运行 frontend build、pytest、ruff 全套，并再次核对生产 PID、端口与数据库路径。
