# Profile 看板后端方案：复用现有记录

2026-09-06。方案已按后续实施授权落地，保留下面的设计依据。实现与测试使用隔离数据库，不包含生产数据库扫描或性能压测。

## 结论与范围

不增加 agent 采样、采集字段、数据库表、字段、索引或持久化统计；不调整现有高频缓存和历史保留时间。新增工作限于一个 Lab 个人活动只读接口、内存中的区间聚合，以及原 Jobs 查询的历史范围兼容。图表数量不对应查询数量：整页共用一份活动聚合结果。

仅拼接现有 HTTP 接口无法完整实现当前看板。新增一个小型聚合接口比扩大多个公共接口、下载全量任务后在浏览器逐项补查更合适。

## 已确认的实施约束

1. 不增加采样，不修改数据库结构，不新增统计持久化。
2. 最低分辨率（1h）的任务历史访问范围可延长至 30 天；这不是将高频缓存保留 30 天，也不是把时长统计按小时取整。
3. 已绑定同一 Lab 用户的跨节点 Linux 账号合并统计；未绑定账号继续作为独立统计主体。
4. 实施仅在独立功能分支及预览环境中进行，生产发布不包含在本次工作中。

## 跨节点账号的统一统计主体

在计算任何时长之前，先解析活动属于谁。使用稳定的 Lab 用户 ID 作为已绑定主体，显示名仅用于展示，不能以 `kuma` 这个字符串作永久主键。

| 原始账号 | 绑定关系 | 统计主体 |
| --- | --- | --- |
| a / usra | 绑定用户 kuma | Lab 用户 kuma 的 ID |
| b / usrb | 绑定用户 kuma | 同一个 Lab 用户 ID |
| c / usrc | 未绑定 | 独立账号 c / usrc |
| d / usra | 未绑定 | 独立账号 d / usra，不因与 a 同名而合并 |

未绑定主体优先以 `(node_id, unix_uid)` 标识，用户名只用于展示；历史记录缺失 UID 时用 `(node_id, username)` 作为未绑定回退主体，不据此自动认领到 Lab 用户。归属信息完全缺失时保留明确的 Unknown 标识，不推断真人身份。

绑定关系按有效期匹配；同一条记录跨越绑定/解绑/转移时间时按边界拆开。对于同一个时间片，只能分配给一个统计主体：已归属片段不再重复留在未绑定账号行。绑定前的片段保留当时的独立账号归属，不自动追溯认领。

示例：a/usra 用两张卡 2 小时，b/usrb 用一张卡在同一时段运行 2 小时，合并后的 kuma 为 **6 GPU·h、2 小时活跃时间**。跨节点的物理卡必须带节点标识，不会因都叫 GPU 0 而被去重。多个绑定账号在同一天运行，Active days 只计一天。

这个解析器作为 Lab 内的共同能力，供个人页和用户时长统计复用。全局用户统计应先解析绑定、聚合，再排序和截取前 N 项，不能对既有前 20 名结果二次合并，否则会漏掉账号。具体任务仍保留原节点、Linux 账号和 job_key，不把不同节点的两个任务合成一个任务。

未绑定的独立账号继续出现在相应的全局统计中；没有任何绑定的 Profile 不凭登录邮箱或同名账号猜测“我的任务”，沿用无绑定状态。独立版不引入 Lab 身份库依赖；身份解析通过 Lab 扩展层接入。

## 统一的数据来源和归属

历史部分只读以下既有数据：

- 身份库 `lab_account_bindings`：`user_id`、`node_id`、`unix_uid`、`valid_from`、`valid_to`。
- 遥测库 `process_sessions`：会话身份、`user_uid`、进程/父进程启动时间、名称、首末观测、状态。
- `process_gpu_usages`：每个会话在每张 GPU 上的首末观测。
- `gpus`：设备名称、UUID、物理卡标识。

两个数据库保持原样。服务端先用当前登录用户读取绑定，归并重叠的绑定有效区间，再将节点、UID、时间条件作为参数交给遥测只读查询；不迁移身份、不把身份信息写回遥测库。

按 `(node_id, user_uid)` 匹配，不能只凭用户名。历史绑定通过既有 `list_bindings(user_id=..., active_only=False)` 读取。归属区间为：

```text
GPU 使用记录 ∩ 绑定有效期 ∩ 请求日期范围
```

已结束的绑定仍保留其有效期内的个人历史；重新分配后的新活动归新用户。默认不把绑定前的历史追溯归给刚注册的用户。旧记录没有 UID 时不凭同名认领：在全局统计中按独立账号回退，在个人统计中标为归属信息不足，不要求数据库补写。

当前接口使用登录身份，不接受任意 `user_id` 替代本人。沿用既有 Lab 权限，不改变公共 Jobs 的可见范围；个人页筛选在服务端完成。

## 看板指标如何计算

计算内部使用秒和完整精度，只在展示时转为小时并四舍五入。所有组件使用同一个 `as_of` 和时区。7/30 天定义为 Asia/Shanghai 的最近 7/30 个自然日，包含今天，最后一个区间截止 `as_of`；跨午夜分开显示，同一任务保留同一 key。

| 页面内容 | 计算方式 |
| --- | --- |
| GPU hours | 按物理 GPU 合并本人多个会话的重叠时间段，再求持续秒数之和 / 3600。4 张卡使用 2 小时为 8 GPU·h；两个进程共享同一卡的同一小时只计一次。 |
| Time with active jobs | 对所有 GPU 的记录区间再次取时间并集，不乘卡数。 |
| Active days | 有本人 GPU 观测记录的自然日数。单次观测的零长度记录仍可计为活跃日，但不能凭空补成一段运行时长。 |
| Weekly activity | 对物理卡区间起止事件做一次扫描，产生并行卡数的变化段；与每日边界相交，合并相邻相同数量的片段。日展开再提供具体任务区间。 |
| Your GPUs | 对上述物理卡时长按型号分组，再除以该周期总时长；型号未知时保留 Unknown，不能丢失时长。 |
| Busiest hours | 将相同记录区间分配至本地小时，按绑定有效期内的可统计日历时长归一化，计算最高的连续 3 小时窗口，允许跨午夜，固定平局规则；只有摘要文字。此结果仍是基于记录区间的估计，不能声称排除了所有采集缺口。 |
| Recent jobs | 复用 `job_key()` 的既有分组规则，保持与 Jobs 可定位关系；列表分页不影响统计总量。 |

物理卡识别复用现有规则：普通 GPU 为节点 + UUID，已有 Ascend 多 die 情况按物理 card 标识去重。独立版 overview 保持原有按会话累加口径；Lab 的用户时长行通过扩展回调使用同一归属解析和物理卡并集，任务排名等其他统计保持原有口径。

不能用 `任务总时长 × 出现过的 GPU 数`：任务可能中途增减卡。不能直接累加各任务时长：同一卡可能被多个任务共享。

## 精度边界：不为 Demo 补造数据

`process_gpu_usages` 的主键是会话 + GPU，更新的是首末观测和计数，没有完整的进程存在/消失事件序列。`process_sessions.duration_seconds` 也是首末观测之差。

因此第一版可以提供记录范围及其估计时长，不能保证其中每一分钟持续活跃，也无法精确恢复任务在同一卡上消失后再出现的间隙。`sample_count` 不能单独还原缺失时刻。

- 指标信息提示统一使用 “Based on recorded task intervals”。
- 图中的空白表示没有该用户的已归属记录，不能证明设备空闲；文字采用 “No recorded activity”。
- 不发布无法证明的 coverage 百分比，不把 Demo 中手工构造的缺失区间当成后端已经具备的能力。
- 可返回 `accuracy: observed_intervals`、`coverage: unknown`，以及可确定的记录范围。没有 UID、存储未启用、数据不可用与真正没有记录应区分。
- 现有 GPU rollup 是设备级数据，不能凭它证明某个用户的进程持续存在。
- raw snapshots 默认不启用保存，即使启用默认也仅保留 12 小时；不能依赖它支撑 30 天个人活动，也不为此修改配置。

## 最小接口增量

已新增：

```text
GET /api/lab/me/activity?range=7d
```

返回一份统一结果：

```text
range / timezone / as_of
accuracy / coverage / availability
summary                         周期总量
days                            每日总量及并行卡数时间段
gpu_models                      型号时长与占比
busiest_hours                   高峰摘要
jobs.items / next_cursor        当前筛选下的任务列表
```

同一接口可以接收 `date`、`gpu_model`、`status`、`q`、`cursor`，支持日展开和任务分页。首屏返回概览与首屏任务；任务行按需加载其会话/GPU 记录区间。响应将周期总量和选中范围总量分开，避免筛选后偷偷改变顶部数字含义。

查询模型筛选或日期展开时复用服务端缓存中的已归属区间，不重新扫描原始遥测。对于大量任务，明细分页，聚合从完整匹配集合计算，禁止把前 500 条当总量。分页游标绑定当前快照版本及筛选条件；过期时明确重新加载，避免继续在变化的结果中跳页。

复用现有的详情、GPU、Performance 三类接口，不另造曲线端点。正式实现时需要小幅扩展：

1. Jobs 查询支持明确的 30 天范围，保留既有默认 7 天行为；避免改一个常量就让所有旧请求扫描 30 天。
2. `get_job()` 能定位 30 天里的已知 key，优先按 key 的节点/进程身份约束查询后验证原分组 key，或显式传入有上限的历史范围；不能只改列表、让详情和曲线继续 404，也不能放开为无界全库扫描。主服务与 sidecar 路由保持一致。
3. 按确认的范围扩展历史：最近 7 天沿用原精度策略；7–30 天的任务通过既有 1h rollup 访问，Auto 对这段历史选择 1h，不承诺更细分辨率。列表支持显式请求 30 天，默认请求仍可保留 7 天以控制扫描成本；详情和曲线能定位列表返回的同一个 job_key。30 天指回看范围，不是单个任务的最大运行时长。跨越精度边界的完整曲线使用可覆盖窗口的 1h 数据，明确实际分辨率。
4. 现有保留期不变：20s 默认 7 天、2m 默认 60 天、1h 默认 365 天。小时查询包含任务开始所在的汇总桶，避免一个小时内的短任务查不到点；但该点覆盖整个小时，不能冒充进程独占数据。未采到的 Performance 仍显示不可用。
5. 前端 Jobs 路由支持通过 `job_key` 精确选中已知任务。目前进程跳转只带 PID、node_id、since；不能假定它会自动定位过去 30 天里的同一项。

## 查询和刷新成本

- 首屏复用已有 `/api/lab/me` 和 App 的 cluster 订阅，只增加一次活动请求。向 Profile 传入 App 已有 snapshot/context，避免重复请求集群快照。
- 历史统计建议最多每 60 秒刷新一次，仅页面可见时触发；日/型号切换尽量使用缓存。它是接口刷新间隔，不改变 agent 采样。
- 服务端使用有容量和字节上限的短期内存缓存，默认 TTL 60 秒；按用户、规范化日期范围、时区、绑定指纹隔离。一个键同时只执行一次聚合，避免多标签页重复计算。不增加 Redis、定时任务、落盘缓存或后台常驻聚合。
- 身份/绑定变更后使缓存失效；缓存的 `as_of` 随响应返回，不能标成当前秒的新统计。近期运行状态与历史统计的更新时间分开。
- 运行中任务复用新鲜 cluster snapshot；数据库的 ended 清理由现有定时逻辑维护，不能仅凭库中 `status=running` 判断仍在运行。节点离线、快照不新鲜或进程可见性不足时显示状态未知/最后观测，不把断线当任务结束，不无限延长历史时长到现在。
- 详情只在用户展开时请求；GPU / Performance 只请求当前选中的视图和指标，不预取每个任务的曲线，不为 Profile 单独向 agent 发 RPC。
- 按节点、归属 UID 和相交时间条件约束查询，复用已有 `(node_id, first_seen_at, last_seen_at)` 使用记录索引及 session 主键。现有索引并不保证多年历史下的理想性能，需要在隔离数据上看查询计划和耗时，不能预先承诺几十毫秒。
- 新聚合可通过有界工作线程和独立只读连接查询已有遥测库，避免阻塞主事件循环或并发使用采集写连接。连接使用只读 URI，避免调用带初始化/迁移的 `SQLiteStore.open()`；不以本功能触发建表或维护。
- 如果完整查询超出预算，返回明确的暂不可用/缩小范围提示，不静默截断总量。先优化查询与缓存；新增索引或汇总表不属于本次方案。

## 实现与验收记录

本次交付的页面为 `/profile`，原账号设置迁至 `/profile/settings`，旧 `/account` 地址仍可进入账号设置。新增接口返回 `summary`、`selection`、`days`、`gpu_models`、`busiest_hours`、`jobs` 和 `day_jobs`；日展开最多显示 100 个任务并明确总数，其余可在 Recent jobs 中翻页。分页游标过期返回 409，客户端重新加载。
